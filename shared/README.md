# BRAWL 共通仕様 — 二重管理を終わらせるためのルール

## この仕組みの現時点の状態

- [brawl-core-contract.json](./brawl-core-contract.json): **共通仕様の期待値（契約）** と、人数/モードで意図的に違う項目の登録簿。
- [shared-rules-parity.cjs](../tests/shared-rules-parity.cjs): 現行の `1v1-combat-evolution-test.html` と `2v2-ui-guardian-r4-test.html` の実コードから、HP・速度・射程・攻撃力・リロード・当たり判定半径・潜伏発見距離・既存の共通バランス・ガス・自然回復・ガンナーの3連射間隔・ULT獲得係数を抽出し、契約との一致を確認。
- [GitHub Actions](../.github/workflows/shared-rules-parity.yml): どちらかの候補HTMLやこの契約が変わるたび、テストを実施。片側だけ速度や攻撃力を変える人工ミューテーションで失敗することも毎回確認する。
- **重要:** この段階は「一致を監視する」だけ。まだ両HTMLが単一の実装をインポート/生成しているわけではない。今のルール定義だけ編集してもゲームは変わらない。現行版のアクション、UI、Firebaseには触れていない。

## やりたい完成形（まだ未実装）

1. `src/shared/` に戦闘数値・武器挙動・ガジェット・ウルト・判定・プレゼンテーションの共通実装を集約。
2. `src/modes/1vs1/` と `src/modes/2vs2/` には人数、マップ、勝利条件、カメラ、味方連携のような**モード固有**処理だけ置く。
3. 共有ソースとモード固有ソースを `scripts/build-brawl.mjs`（要実装）で統合して、学校iPad/Google Sites向けにも単独ファイルとして動くHTMLを**毎回両方生成する**。CSPで外部JSが制限されることがあるので、単に新JSファイルを別参照にするだけでは不十分。
4. 2人/4人・異なるマップで同じ武器挙動になるかのシミュレーションテストと、スマホの操作ボタン衝突テストを追加。1vs1/2vs2両方が合格するまで採用しない。
5. 現行試遊版は保存。次に生成する独立候補だけで比較してから切り替える。オンラインGoogle Sites・Firebaseへの反映はさらに別の承認・実機検証を要する。

## 意図的に同一化しないもの

- 1vs1/2vs2の人数、マップの大きさ、ガスの到達上限、勝利条件、カメラ。
- タンクの味方を守る能力は2vs2専用。1vs1のガジェットには別の役割を与える可能性があるので、無条件コピー禁止。
- Firebaseの部屋ツリー（`rooms` と `rooms2v2`）とプロトコルは互換確認なしに混ぜない。

## 現在未統一であるもの

詳しくは契約ファイルの `mismatchesToResolveBeforeClaimingParity`。代表例: タンクの散弾角、ガンナー3連射の発射位置、ULT中のリロード、スナイパーGADのノックバック距離、BOT判断、戦闘処理アーキテクチャとUI。**これらをテストが合格しただけで統一済みとは呼ばない。**

## ユーザーの最新フィードバック（2026-10-12）

- **R4の守ったダメージ数値と大きな通知は邪魔。** 次の新候補では数値・派手なテキストを外して、防御リング、線、被弾時の軽いエフェクトのみとする（現行R4にはまだ実装されていない）。
- R4のUI自体は「かっこいい」という評価。UIの土台を残しつつ、視認性・操作優先で整理する。
- 手動の1vs1/2vs2擦り合わせを毎回繰り返すのをやめ、ゲーム共通のルールは1か所から両モードへ一斉反映できる方式を目標にする。

## 開発ルール

- 両HTMLの手編集で共通ロジックの差分を意図なく作らない。
- 単一ソース化の完了前に共通項目を変更する場合は、現段階の検査が通ることを確認する。
- 仕様そのものを変更する場合、契約と両方の独立候補、およびテストを同じ作業で更新する。片方のみを無理にPASSへするために契約を曲げない。
- 新たに差が判明したら契約の「既知の未統一」へ記録し、**理由を判断してから**統一する。
