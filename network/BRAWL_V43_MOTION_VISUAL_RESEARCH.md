# BRAWL V4.3｜4人実戦風テスト・映像レビュー・外部研究

対象：生成された開発用通常/ドラフト2vs2。公開中Google Sites、Firebaseの本番DB/Rules、Driveは触らない。2026-10-21。

## なぜ実戦風の動画を撮るのか

V4.2までは4人の端末が接続し、短い発射やラウンド進行は検証できたが、プレイヤーが大きく移動し続ける局面を視覚的に評価できなかった。V4.3では**実際のキーボード移動イベントを通した4人の移動＋射撃**をそれぞれ27秒継続する。通常2vs2・ドラフト2vs2で試す。宿主/ゲストそれぞれをWebKit録画、途中で複数回スクリーンショットを残す。ブラウザは1024×650のタッチデバイス相当。ただし移動はスクリプトが押すキーであり、実際の指を使う学校iPadのタッチ操作を再現したものではない。V3.4までのタッチ操作テストを別途維持。

4キャラはガンナー・タンク・スナイパー・ボマーに分ける。発射は元のshootAngle関数から通常のACTION/Firebase/ホスト判定を通る。1人のゲストだけ発射イベントのコールバックに180msの**人工待機**を入れ、ゲーム状態受信との差を観察する。これはRTTではない。

## レビュー観点（数値と別に目視）

- 自分が発射した弾が自然に出るか、他人の弾が突然現れる/巻き戻る/消えるか。
- 移動中の敵が瞬間移動して見えないか。位置の補間が壁を横切って見えないか。
- ボマーの弾道、追従カメラ、低速画面、復活・ラウンド切替の一貫性。
- HP/弾数/ミニマップ/スコアの見やすさ、画面内でHUDや操作ボタンが邪魔にならないか。
- キャプチャされたvideo.webm自体のフレーム落ちと、実ゲーム画面のラグを混同しない。WebKit仮想ブラウザが快適でも学校Wi-Fiの結論にはならない。

## 外部資料（調査根拠）

- Firebase [Optimize Database Performance](https://firebase.google.com/docs/database/usage/optimize)：更新の頻度とデータの量を測ってから構造・リスナー効率を改善。リスナーは可能な限り必要な下位パスを購読する。現状の game.value は全ゲーム状態を購読するため計測が必要。
- Firebase [Read and Write Data on the Web](https://firebase.google.com/docs/database/web/read-and-write)：ローカル書き込みイベントが実サーバー到達前に発火することがある。ローカル表示の速さをそのままリモート配送速度と誤認しない。
- Gaffer On Games [Snapshot Interpolation](https://gafferongames.com/post/snapshot_interpolation/) と [State Synchronization](https://gafferongames.com/post/state_synchronization/)：補間はカクつきを減らす反面、遅延が加わる。ジッターで状態の到着が不均一になることもある。これらのUDP/専用サーバー前提の数値をそのままFirebase SDKへ当てはめない。

## 計測/成果物

CIのローカルFirebase＋WebKitで両モードを生成し、4人着席/READY/プレイを確認。移動のワールド距離、射撃成功件数、他人の発射イベントの受信件数とV3.9診断の同端末p50/p95、長いframeGapを匿名JSONに保存する。映像はホスト・ゲストの両方、スクリーンショットは6/15/24秒に保存。CI artifactは7日保存し、個人のルームIDは出力に含まない。

数値テストが合格しても実機ラグ解消とは言わない。映像を目視してUIと弾の不自然さを分析し、次の小さな描画改善を決める。
