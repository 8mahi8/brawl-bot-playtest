# BRAWL — 1vs1 / 2vs2 通信を無理に一本化しない開発基盤

更新: 2026-10-12。これは**オフラインでの通信設計・疑似負荷テスト**。Firebaseの本番通信、Google Sites、学校iPad実機には接続・変更していない。

## 公式Firebase RTDBエミュレーター実通信試験が成功（2026-10-12）

- [安全なエミュレーター用Rules/起動手順](./emulator/README.md)、[実行テスト](../tests/network-firebase-emulator.cjs)と[独立CI](../.github/workflows/firebase-emulator-lab.yml)を追加。実際のFirebase RTDB SDKを使い、`/lab/pair`と`/lab/squad`のローカル読み書き・権限判定を検証。
- **41件PASS**。2人/4人の認証済みテストクライアントが位置・操作を書き込める一方、未参加者・匿名アクセス、他人の位置、重複seq、古いround/life/motionRev/connectionId、ホストUID奪取、勝手なHP変更を拒否。
- さらに、1vs1・2vs2それぞれで**ホストのRTDBトランザクションが成立し、別クライアントが`value`リスナー経由で更新後のHPを受信**した。
- [Actions成功](https://github.com/8mahi8/brawl-bot-playtest/actions/runs/38249662523)。**実Firebase SDK＋ローカルエミュレーター**の検査であり、インターネット越しの本番RTDBや実Firebase Authのログイン・学校iPadを検証したわけではない。
- 特権で投入したroom/member/host情報はあくまでテスト用。**安全なルーム作成・ホスト選出/交代・権限を持つサーバーの実装は未完成**。試験Rulesも本番用ではない。

## 決めた原則

**「共通にできる」だけでは共通にしない。** 共通化は保守コスト・安全性・測定可能性が改善するときだけ。

| レイヤー | 1vs1 | 2vs2 | 扱い |
|---|---|---|---|
| 戦闘計算 | 共通契約からビルド | 共通契約からビルド | ✅ 共有済み |
| ルームとプロトコル | `/rooms`・保存済みオンラインV2.8は `PROTOCOL=28` | `/rooms2v2`・保存済みオンラインALPHA10は `PROTOCOL=3010` | **分離**。新BOT生成版（29/3011）のプロトコルと混ぜない |
| 位置更新 | 2つの役割（host/guest）。既存80ms送信 | 4席、既存80ms送信。host tickは100ms | **分離**。固定値のまま実測に入る |
| 接続識別 | 旧V2.8は役割/オンライン真偽を保持。明示の connectionId は位置payloadにない | connectionId・presence・matchId・round・life・motionRev・seq を位置に含む | **分離**。2vs2の再接続検証を1vs1に押し付けない |
| ダメージ・勝敗 | 既存V2.8は `/game` transaction を使用 | 既存ALPHA10はホストがactionキュー・combat tickを処理 | **分離のまま**。権限・送受信形態が違う |
| UI補間 | 1人の相手を短く予測 | 3人の他プレイヤー＋味方/敵の補間 | モード専用。見た目の安定度で調整 |
| 遅延・受信測定 | p50/p95/最大遅延、相手の位置Age、書き込み成功/失敗 | 同項目＋4人の更新分散、ホスト処理回数、戦闘状態の書き込み競合 | 計測項目の**意味だけ共有**し、実装は別々でもよい |

## 今回作った実装（ライブ適用ではない）

- [1vs1専用通信検証モジュール](./lab/one-vs-one.cjs)：`host/guest`のround・seq・座標検証、80ms送信基準で最新移動へまとめる処理、予測150ms上限、切断・世代変更時の古い位置の破棄。
- [2vs2専用通信検証モジュール](./lab/two-vs-two.cjs)：4席・matchId/round・connectionIdとpresence・life・motionRev・seqの検証、再接続と復活の世代切替、4人の位置の一括取込、送信のまとめ処理。対象画面の縦横・半径は引数で設定可能。
- [モード独立の回帰テスト](../tests/network-mode-isolation.cjs)：12カテゴリ。後から届いた過去ラウンド、古い接続・復活前の操作、範囲外/非数値、二重・逆順データ、送信が偏った場合を防止。
- [疑似遅延負荷テスト](../tests/network-latency-simulation.cjs)：16ms描画ループ・80ms送信で2秒間、0/150/300/600msの固定遅延に模擬ジッタを加える。これはネットワークの実測でもサーバー容量保証でもない。
- [公開隔離チェック](../tests/network-public-isolation.cjs)：既存BOTページと生成候補が `connect-src 'none'` を維持し、FirebaseデータベースURLやオンライン接続を誤って公開しないか確認。
- [自動CI](../.github/workflows/network-mode-lab.yml)：上記を変更時に自動実行。ゲームUIや戦闘ロジックのテストとは独立したジョブにする。


## 模擬負荷で確認できたこと

描画16ms・位置書き込み80msを2秒間の疑似環境で評価。位置書き込みは **1vs1: 52件、2vs2: 104件**。4人では位置ストリームだけで約2倍。さらに2vs2は戦闘ホストのtransactionや状態配信が必要になる。モデルは逆順到着での重複・古い位置を除外した。

**重要:** 0/150/300/600msの遅延設定で「操作が問題なく快適」と検証したわけではない。表示の補間・入力の遅延・Firebaseコスト・学校ネットワークの挙動は実測が必要。

## 追加した複数クライアント統合試験（オフライン）

- [network-multiclient-integration.cjs](../tests/network-multiclient-integration.cjs) は生成版の**本物のV8戦闘エンジン**と、1vs1・2vs2それぞれの独立した模擬通信モジュールを接続する統合テスト。
- 2人と4人について、位置送信→受信フィルタ→ホストの射撃受理→弾の命中→HPの減少→全クライアントへの確認済みHP配信を再現する。重複攻撃、逆順の旧戦闘スナップショット、旧ホストトークンと旧combatRev、切断した接続・旧ルームからの位置データも除外する。
- **テストで発見した実際の仕様差を修正。** 1vs1生成版のV8ガンナー連射は3発同時だったのに対し、2vs2は105msずつの時間差だった。1vs1のV8弾を `spawnAt` 付きで発生させ、時間差に応じた移動時間を計算するよう変更。実エンジンの両モードで最初のtickに10ダメージ、次のtickで合計20、3tick目で合計30となることを検査。昔の比較用HTMLは変えていない。
- **0/150/300/600msは人工的な遅延設定。** この統合試験は実Firebaseクライアント・Firebase Auth/Rules・再接続の実装・実ホスト選出・Google Sites埋め込み・iPad Safari操作を検証しない。古いホストのトークンが拒否されることのみ検証し、本当のリース獲得/選出を再現したものではない。
- [統合CI](../.github/workflows/network-mode-lab.yml) は生成されたゲームHTMLも変更監視対象に含む。通信モデルと戦闘エンジンの境界で不整合が生じればCIが止まる。
- [戦闘・UI本体の回帰CI](../.github/workflows/foundation-build.yml) でも生成結果が古くないか、1vs1 PC/タッチと2vs2の4サイズBOT試遊を検査している。

## 次にネットワークを実装する際の段取り

1. 旧オンライン元版（Driveに保存されているV2.8 1vs1、ALPHA10 2vs2）を保護する。公開GitHubのBOTページに秘密のDB URLや学校固有情報をコピーしない。
2. 本番以外の**適切なRules/Authを備えた隔離環境**で、それぞれの通信実装を別候補として作る。古い `PROTOCOL=28/3010` のルームと直接混在させず、プロトコル変更やRoomルートは個別に管理。
3. 1vs1では相手の位置・弾・HPと2人のReady/退出の遷移、再接続を検証。**旧版は明示のconnectionIdを位置payloadに含まず、旧ラウンド・seq・リロードで不正受理が起こり得ないかを検証**する。
4. 2vs2では4席のpresence/connectionIdの置き換え、ホスト移行、重複action・旧life/round、遅延中のダメージ確定を優先。書き込み頻度を下げる前に、位置・action・combat game transactionを**別々に計測**する。
5. 測定項目はサーバー時刻差、位置書き込み回数、受信更新間隔、成功/拒否件数、ホストtransaction試行/競合、最大・p95遅延、復帰所要時間、端末FPS。個人ID・ルーム番号・認証情報・生位置データはログに残さず集計値のみ。
6. 2台で1vs1、4台で2vs2の実機試験。0/150/300/600msの遅延・再接続・Safariスリープ・ホスト切断・技連打・再戦。測定に基づいて人数別に更新周期と同期対象を調整する。更新頻度の「低いほど良い」は禁止。
7. 実DB・Rules・Google Sitesの公開環境に触れる試験や移行は対象と影響を特定し、ユーザー承認後に実施する。

## 明確に未完了の点

- このネットワーク検証モジュールは**GitHub Pagesの実ゲームにも、Drive上のオンライン元版にも接続していない**。純粋な設計・検査用。
- Firebase Realtime Databaseの実読み書き、権限/認証、課金/負荷、ブラウザ/学校端末の実通信、オンライン4人BOT/人間対戦は未検証。
- 最新BOT生成版のマップは2vs2が1536×860/R18。古いALPHA10は1000×600/R20。オンライン候補を作る際はマップ・カメラと座標検証を**旧固定値のまま使わず、対象版の寸法に合わせる**。
- 2人と4人のネットワークモジュールを統一する予定は**ない**。共通化するのは実測の指標、またはコードの共有が本当にメリットを生む部分に限る。
