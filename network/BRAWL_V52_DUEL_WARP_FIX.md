# BRAWL V5.2 — 学校iPad 1vs1ワープ描画の切り分け・候補修正

## 不具合報告
2026-10-22: 以前は学校Safari iPadで正常だったBRAWL 1vs1が、4モード統合ZIP「BRAWL_V3.7_GoogleSites_4modes.zip」を各Google Sitesページに別々に貼った後、キャラがワープして画面もカクカクする。

## 調査で確定したこと
- Drive保存の旧V2.9（10月13日）とV3.7通常1vs1（10月20日）を実物で比較。4モードZIP中の通常1vs1と個別V3.7 TXTは一致。
- 位置送信、位置予測、メインループの基本ソースは両版で同じ。新版はデフォルトのCanvas縦幅が70%→100%だが、これだけが原因とは言えない。
- Chromium DPR2 SOLOのフレーム計測は両方約60fps。CPU4倍スロットルは両方p95約50ms、8倍スロットルは旧版p95約166.7msとV3.7 p95約66.7ms。新版の描画負荷だけが悪いという再現ではない。
- V5.1 WebKitローカルFirebase比較でも旧固定公開版と共通基盤版は両方低fpsで、新版だけの悪化は再現できなかった。
- V3.7のremote表示補間は、離れた予測位置と現在の表示位置の差が125を超えると、キャラをその位置に直接飛ばしていた。

## V5.2 STAGING修正
1. 通常歩行では位置差による強制テレポートをやめ、既存の指数補間だけを使用。意図的なダッシュ/ジャンプでの即時補正は維持。
2. Safari resize・ResizeObserverが同じ画面サイズを通知しても、Canvas幅高を再設定しない。これらへの代入は画像をクリアしバッキングストアを再確保する。実際のサイズ変更には追随。
3. 通常・ドラフトの1vs1の生成版のみ変更。2vs2、固定公開HTML、Firebase、Google Sites本番は変更しない。

## 実ブラウザでの再現
Chromium実ゲームSOLO状態にテスト限定の位置差約220を注入し、1 simulation stepあたりの最大相手座標変化を測定：旧V3.7通常版218.33単位 → V5.2候補56.59単位。両者JavaScriptエラー無し。
この修正は意図しないワープの一つの再現可能な経路を解消したが、学校iPadで起きるカクつきの根本原因を確定・解消した証明ではない。

## 次の判断
WebKit/Firebaseエミュレーターと静的回帰テストが合格した後で学校実機テスト候補として扱う。実機テスト前に通常公開版を勝手に貼り替えない。改善しなければ実Firebase受信間隔、Safari iframeと描画停止、gameLoopの低fps時時間切捨てを分けて調べる。
